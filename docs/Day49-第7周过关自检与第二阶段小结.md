## 1. 过关标准逐条自检（先看真实状态，再决定补什么）

### 标准①：支持 100 份文档批量上传

| 检查项 | 你的状态 |
|---|---|
| 批量上传接口 | ✅ `/api/documents/batch/upload`（Day43） |
| 异步不阻塞 | ✅ 虚拟线程 + `@Async`，秒回 taskId |
| 进度反馈 | ✅ `GET /batch/{taskId}` 返回状态机 |
| 失败重试 | ✅ `@Retryable` 3 次指数退避 |
| **100 份的量** | ⚠️ 需实测：`max-request-size: 200MB` 是否够、100 文件并发是否稳定 |

> **待验证**：你 `application.yaml` 的 `max-request-size` 还是不是 200MB？100 个文件一起传，请求体别超限。真正的"100 份"靠的是**异步 + 批量**架构支撑，不是靠一次能传多少 —— 架构你已经对了，剩下是压测验证（Day74 再做）。

### 标准②：用户权限隔离

| 检查项 | 你的状态 |
|---|---|
| owner 元数据打标签 | ✅ `attachIdentity` 写入 `owner`（Day45） |
| 检索过滤 | ✅ `/vector/search` 用 `FilterExpressionBuilder.eq("owner", ...)` |
| 问答过滤 | ✅ `/ask` `/askWithSource` 通过 `qa_filter_expression` 动态过滤 |
| **鉴权来源** | ⚠️ 还是 `currentUser` 参数模拟，**没到登录态** |

> **待补**：权限隔离的**逻辑**已对（同一套数据，不同 user 检索结果不同），但**身份来源**还靠前端参数，安全上是假的。Day45 文档里明确标了这是「演示用」，正式补要到 Day82 权限管控。第 7 周过关**只需逻辑隔离生效即可**，安全升级记入 Day82。

## 2. 实操作业（80 分钟）—— 补齐两个缺口

> 目标：把 Day46 的 debug 检索接口 + Day47 的生成评估补齐，让「量化效果」完整。

### 缺口一：落地 `RagDebugController`（Day46 排查接口）

新建 `src/main/java/com/example/springai/controller/RagDebugController.java`：

```java
package com.example.springai.controller;

import com.example.springai.service.MultiRecallRagService;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import java.util.Map;

@RestController
@RequestMapping("/api/debug")
@RequiredArgsConstructor
public class RagDebugController {

    private final MultiRecallRagService multiRecallRagService;

    /** 排查召回：看清每一步。GET /api/debug/retrieve?question=报销要多久 */
    @GetMapping("/retrieve")
    public Map<String, Object> debugRetrieve(@RequestParam String question) {
        return multiRecallRagService.debugRetrieve(question);
    }
}
```

配套：在 `MultiRecallRagService` 里补 `debugRetrieve(question)` 方法（Day46 文档 §3 步骤 1 有完整代码）。
