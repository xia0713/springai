## 1. 四维度规范骨架（已按你的真实经历预填）

### 维度一：稳定性（Day71）

**核心原则：瞬时重试交给框架，外层只做熔断/路由/降级/限流 —— 永不叠加 Retry。**

- [ ] 五层体系齐备：内建重试(L1) → 熔断(L2) → 多模型路由(L3) → 降级链(L4) → 限流(L5)
- [ ] 熔断参数有依据：minimumNumberOfCalls ≥5（防单次抖动）、OPEN 等待 ≥10s（LLM 故障是分钟级）
- [ ] 降级链每级标注服务等级（[备用模型]/[缓存答案]/[服务降级]）
- [ ] chaos 注入点在被注解方法体内（外部抛不计入熔断统计）
- [ ] 熔断即交接班：介入单含 终止原因/卡点/轨迹/建议

**红线：外层 @Retry + 内建重试 = 9 次调用风暴。**

### 维度二：成本（Day72）

**核心原则：缓存命中 → 0 token；输入 token 是输出的 5-20 倍 —— 只盯生成费会算错账。**

- [ ] 优化按性价比排序：缓存 > 砍输入 > 换便宜模型 > 砍输出
- [ ] 缓存 key 必须归一化（strip+小写）+ **含用户/权限维度**（个性化答案进共享缓存 = 隔离事故）
- [ ] 缓存 key **含 prompt 版本维度**（否则灰度回滚被缓存击穿 —— Day76 交互坑）
- [ ] 时效类答案必须 TTL（"今天天气"三天后还在 = 事故）
- [ ] 统计口径常驻：cacheHits / 模型分布 / tokensSaved —— 没有口径的优化是感觉

**红线：个性化答案进共享缓存。**

### 维度三：性能（Day74）

**核心原则：先测量后优化 —— 分层压测定位瓶颈层，看 P95 不看平均值。**

- [ ] 压测分三层：底座（缓存路径）/ DB 路径 / LLM 路径 —— 别混成一锅粥
- [ ] 口径：P95/P99 + 成功率 + 吞吐；平均值会骗人（95 个 0.1s + 5 个 5s 的例子）
- [ ] 连接池乘法账：每副本 Hikari × maxReplicas ≤ PG max_connections
- [ ] 索引决策写明"做/不做 + 理由 + 触发条件"（如：3072 维暴力扫描，数据到 5 万条前做低维重建）
- [ ] LLM 调用绝不占着 DB 连接（无事务方法用完即还；禁止 @Transactional 里调 LLM）
- [ ] 流式是真流式（任何 collectList().block() = 假流式）；价值是 TTFT 不是总耗时
- [ ] 压测数据量接近真实（3 条向量压不出暴力扫描问题）

**红线：没测基线就宣布优化成功。**

### 维度四：部署与发布（Day75/76）

**核心原则：无状态是水平扩展的前提 —— 内存态是部署期才爆炸的隐形炸弹，写代码时就要体检。**

- [ ] 无状态化体检表（7 项资产逐个外置：ChatMemory→JDBC / 进度→PG / 工具态→落库 / 缓存→Redis）
- [ ] 探针语义分清：liveness 只判进程活（放重逻辑 = 下游一抖全集群被杀）；readiness 判流量
- [ ] 探针 initialDelaySeconds 给足（Spring 启动 20-40s，太短 = CrashLoopBackOff）
- [ ] 配置外置：敏感走 Secret（且知道 Secret≠加密）、非敏感走 ConfigMap（Spring 环境变量覆盖）
- [ ] 发布走灰度：提示词版本注册表 + hash 确定性分流 + 秒级回滚（percent=0）+ per-version 审计
- [ ] 镜像构建环境假设显式化（toolchains 陷阱：本机能构建 ≠ 镜像里能构建）

**红线：带内存态状态上多副本（单测全过、单机全通、上集群薛定谔出 bug）。**

## 4. 关键提醒

1. **规范的价值在使用不在写作** → 下个项目开工第一天把上线检查单贴出来，才是规范生效的标志。
2. **别写成教科书** → 每条规范必须能回答"这条对应我们哪天踩的坑"，答不出来的条目删掉或降级为"了解项"。
3. **规范要随项目长** → 季度评审不是形式：新踩的坑升级成规范条目，被证明多余的条目删掉。
