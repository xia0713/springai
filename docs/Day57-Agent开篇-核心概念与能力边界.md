## 0. 先泼一盆冷水：Agent 被严重神话了

2025-2026 年"Agent"是最热的词，也是最被滥用的词。开始之前建立三个清醒认知：

1. **你已经会 Agent 的核心了**。Agent = LLM + 工具调用 + 循环。你第 8 周做的"模型自主选工具、串行调用、中间结果传递"，就是 Agent 的运行时。缺的只是：自主规划、记忆、反思。
2. **大部分号称"Agent"的需求，其实是 workflow**（后面 §2 讲这个关键区分）。
3. **Agent 的可靠性随步数指数衰减**。这不是工程能完全修好的，是原理性约束（§3 有数学）。

Day57 的目标不是"学会 Agent"，是**建立判断力**：什么场景该上、什么场景是坑。

## 1. 核心知识点（40 分钟）

### 1.1 Agent 四大能力（现状盘点）

| 能力 | 含义 | 你的现状 |
|---|---|---|
| **规划 Planning** | 把开放目标拆成子任务、排序、必要时重规划 | ❌ 未做（Day54 报表流程是"你"在 prompt 里写死了步骤，不是模型自己规划） |
| **工具调用 Tool Use** | 选择工具、生成参数、消费结果 | ✅ 第 8 周已精通（@Tool、降级、白名单、审计） |
| **记忆 Memory** | 短期（本轮上下文）+ 长期（跨会话持久化、按需检索） | ⚠️ 只有短期（对话内）；Day59 做长期 |
| **反思 Reflection** | 检查自己的输出/行动结果，发现错误并纠正 | ❌ 未做（Day58/60 涉及） |

**关键理解：四大能力里你已经拥有最重的一块（工具调用），Agent 剩余的部分是"让模型自己做决策闭环"** —— 规划是自己拆步骤，反思是自己检查结果，记忆是跨轮保留经验。

### 1.2 Workflow vs Agent —— 今天最重要的区分

业界（Anthropic《Building Effective Agents》之后基本成为共识）把"AI 自主干活"分成两类：

| | Workflow（工作流） | Agent（智能体） |
|---|---|---|
| 谁决定步骤 | **你的代码/prompt 预先编排** | **模型运行时自主决定** |
| 步骤顺序 | 固定、可预测 | 动态、不可预知 |
| 成本 | 可估算 | 不可估算（步数不定） |
| 可靠性 | 高（每步可测可控） | 随步数衰减 |
| 审计合规 | 容易（步骤固定） | 难（每次路径可能不同） |
| 适合 | 步骤固定的业务流程 | 开放式目标、路径无法预知 |

**对照你的项目：**
- Day54 报表流程「查→写→存→发」—— 步骤是你在 system prompt 里**写死的**，这是 **workflow**（虽然它用了工具调用）。
- Day56 统一助手「问什么答什么」—— 单步路由，也是 **workflow**。
- **真正的 Agent**：「帮我把这个季度的销售情况整理一份分析报告发给相关人」—— 模型自己决定：先查什么、要不要补充查询、分析几轮、发给谁。你事先没写步骤。

**判断口诀：步骤能预先写清楚的，用 workflow（更便宜、更稳、更好审计）；只有路径无法预知的开放任务，才值得上 Agent。** 对 Java 工程师，这个区分格外重要 —— 你们最擅长的恰恰是把流程写确定。

### 1.3 能力边界的残酷数学（为什么长链路 Agent 不可靠）

单步工具调用成功率假设 95%（已经很高了）：

```
1 步任务：  95%
3 步任务：  95%³  ≈ 86%
5 步任务：  95⁵   ≈ 77%
10 步任务： 95¹⁰  ≈ 60%
20 步任务： 95²⁰  ≈ 36%   ← 大部分时候失败
```

**这是乘法衰减，不是工程 bug。** 推论：

1. **Agent 步数越多越不可靠** —— 复杂任务要么拆小，要么加人工检查点
2. **反思能力存在的根本原因** —— 就是用"自我纠错"来对冲衰减（把 95% 的单步通过重试拉回来）
3. **生产 Agent 必须有熔断** —— Day62 你会给 Agent 加异常熔断，就是这个数学的工程对策

### 1.4 真需求 vs 伪需求（作业的核心判断题）

| 场景 | 判断 | 理由 |
|---|---|---|
| 运维排障（根据报错日志自主定位） | ✅ 真需求 | 路径不可预知（可能查日志→查监控→查配置→查代码），Day60 会做 |
| 深度调研（多轮检索+交叉验证） | ✅ 真需求 | 步数取决于内容发现 |
| 复杂客服（查订单+查政策+安抚+升级人工） | ✅ 真需求 | 用户意图组合无法穷举 |
| 固定流程审批（提交→校验→流转→通知） | ❌ 伪需求 | 步骤固定 → workflow/传统代码更稳更便宜 |
| 纯知识问答 | ❌ 伪需求 | RAG 就够，不需要自主决策 |
| 强合规审计场景（金融交易、医疗处置） | ❌ 当前伪需求 | 不可预测路径过不了审计；可做"Agent 出草稿+人执行" |
| 让 Agent "自己学习进步" | ❌ 伪需求 | LLM 不会从会话中持续学习，反思只是当次内纠错 |

### 1.5 框架对比（Java 工程师视角）

| 框架 | 语言 | 定位 | 评价 |
|---|---|---|---|
| **Spring AI + 自研循环** | Java | 工具调用 + Advisor 体系，Agent 循环自己写 | ✅ 你的主线：与 Spring 生态无缝、可控性最强、Day58 就这么干 |
| **LangChain4j** | Java | 全家桶（Agent/RAG/记忆），Spring Boot starter | 可与 Spring AI 对比（Day18 做过），Agent 能力更现成但黑盒更多 |
| **LangGraph** | Python | 图编排/状态机，复杂 Agent 的事实标准 | 思想值得抄：把 Agent 行为建模成"状态+边"，Java 里可用代码模拟 |
| **OpenAI Agents SDK** | Python | 官方轻量 Agent 框架 | 生态绑定 OpenAI |
| **AutoGen / CrewAI** | Python | 多 Agent 协作 | 多角色场景，Demo 炫酷、生产慎用 |
| **Dify / Coze** | 低代码 | 平台化 Agent 编排 | 快速验证用，深度定制受限 |
| **MCP（Model Context Protocol）** | 协议 | 2025 起成为工具/上下文接入的事实标准，Spring AI 1.0 已支持 | 趋势：工具不写在代码里，而是通过 MCP 协议接入 —— 关注 |

**选型结论（Java 本位）**：主业务系统集成 → Spring AI 自研（可控、可审计、贴合微服务）；需要借鉴编排思想 → 看 LangGraph 的状态机模型；工具生态未来 → 盯 MCP。

## 2. 实操作业（80 分钟，不写代码）

> 目标：产出《Agent 能力与场景分析报告》。这份报告的价值在于：以后你公司有人说"我们上 Agent 吧"，你掏出它就能判断是真需求还是坑。

### 报告骨架（`docs/Agent能力与场景分析报告.md`）

```markdown
# Agent 能力与场景分析报告

## 一、Agent 四大能力现状
- 规划 / 工具调用 / 记忆 / 反思 —— 各自含义、成熟度、我们项目覆盖情况
- 核心等式：Agent = LLM + 工具调用 + 自主决策循环

## 二、Workflow vs Agent 边界
- 对比表（步骤决定权/成本/可靠性/审计）
- 我们项目里的判定：Day54 报表 = workflow，什么才是真 Agent
- 判断口诀

## 三、能力边界：可靠性数学
- 95% 单步成功率的乘法衰减表
- 三个工程对策：拆小任务 / 检查点 / 熔断

## 四、真需求 vs 伪需求清单
- 至少 4 个真需求场景（各写：为什么路径不可预知）
- 至少 4 个伪需求场景（各写：该用什么替代——workflow/RAG/传统代码）
- 结合本公司业务：找出 2 个候选真需求场景

## 五、框架选型建议
- 对比表 + Java 本位结论
- MCP 趋势关注项

## 六、结论
- 一句话：什么情况下我们上 Agent，什么情况下坚决不上
```

**写的时候守住两个要求：**
1. 伪需求每条必须写出**替代方案**（用什么做）—— 只会说"不行"不算分析；
2. 结合你自己的业务找 2 个候选场景 —— 报告不是抄概念，是给你公司用的。
