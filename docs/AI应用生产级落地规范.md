## 一、稳定性维度（Day71 沉淀）

### 1.1 分层职责（谁做什么不许越界）

| 层 | 手段 | 负责方 | 本项目实现 |
|---|---|---|---|
| L1 瞬时重试 | Spring AI 内建 RetryTemplate | 框架 | 已配（MultiModelConfig） |
| L2 熔断 | Resilience4j CircuitBreaker | 应用 | ResilientChatService |
| L3 多模型路由 | 主挂自动切备 | 应用 | qwen → deepseek fallbackMethod |
| L4 降级 | 备用也挂 → 缓存 → 兜底话术 | 应用 | 三级链，每级标注服务等级 |
| L5 限流 | RateLimiter | 应用 | 网关入口 20/s |

### 1.2 强制项

1. **外层永不加 @Retry** —— 内建 3 次 × 外层 3 次 = 9 次调用风暴（重试只属于 L1）
2. **熔断参数有依据**：minimumNumberOfCalls ≥5（防单次抖动误熔断）、wait-duration-in-open-state ≥10s（LLM 故障是分钟级，生产 30-60s）
3. **降级链每级标注服务等级**：`[备用模型]` / `[缓存答案]` / `[服务降级]` —— 用户有权知道自己在用哪级服务
4. **熔断即交接班**：熔断输出【人工介入单】（终止原因/卡点/已执行轨迹/处置建议），不是一句干话
5. **chaos 注入点在被注解方法体内** —— 在调用方抛不计入熔断统计，演练是假的

### 1.3 红线

🚫 外层 @Retry 叠加框架内建重试
🚫 降级链无服务等级标注
🚫 熔断只返回异常不返回介入单

### 1.4 真实案例（实测）

- **三态机实证**（Day71）：HALF_OPEN(2 buffered/1 failed) → 1 次失败 → OPEN(66.7%) → 10s → HALF_OPEN → 3 次成功探测 → CLOSED。教训：**OPEN 只持续 10s，观察窗口要脚本化**（"跑不出熔断"的嫌疑犯第一位是观察时机）
- **内建重试实证**（Day59 真实报错栈）：`SpringAiRetryAutoConfiguration` 对 400 抛 `NonTransientAiException` 不重试 —— 框架的瞬时/非瞬时区分是对的，别替它重做

## 二、成本维度（Day72 沉淀）

### 2.1 成本公式与优化优先级

```
月成本 = Σ(输入tokens×输入单价 + 输出tokens×输出单价)
输入是输出的 5-20 倍（RAG 场景：system+检索上下文+历史）—— 只盯生成费会算错账
优化优先级：① 缓存命中(→0) ② 砍输入(压缩/裁剪/收窄工具) ③ 换便宜模型 ④ 砍输出
```

### 2.2 缓存三条 key 纪律（缺一不可）

1. **归一化**：strip + 小写（"你好" 和 "你好 " 必须是同一个 key）
2. **用户/权限维度**：个性化答案进共享缓存 = A 的答案漏给 B（隔离事故）
3. **prompt 版本维度**：否则灰度回滚被缓存击穿（回滚了返回的还是坏版本答案）—— Day76 交互坑

附加：时效类答案必须 TTL（"今天天气"三天后还在缓存 = 事故）。

### 2.3 计量口径（没有口径的优化是感觉）

- 计数器常驻：cacheHits / smallModelCalls / bigModelCalls / tokensSavedByCache
- 真实计量：`ChatResponse.getMetadata().getUsage().getTotalTokens()`（已验证 API）
- 汇报公式：命中率 × 平均tokens × 单价 = 月节省

### 2.4 真实案例（实测）

- **账本实证**（Day74 压测）：50 并发 × 200 请求，cacheHits 恰好 +200，tokensSavedByCache = 16200 = 200 × 81，**分毫不差** —— 统计口径经受了并发考验
- **路由实证**：50 个并发问题全部正确路由到小模型（smallModelCalls +50），规则路由按预期工作

## 三、性能维度（Day74 沉淀）

### 3.1 先测量后优化（分层压测）

```
第 1 层 底座（缓存命中路径）→ 验证 Tomcat/网关/连接池无自伤
第 2 层 DB 路径（检索不带 LLM）→ 量出扫描真实代价，做索引决策
第 3 层 LLM 路径（真问答）→ 瓶颈在上游配额，只验证客户端层无自伤
```

### 3.2 口径

- **看 P95/P99 不看平均**：95 个 0.1s + 5 个 5s → 平均 0.35s 假健康，P95=5s 才是用户体感
- 三件套一起看：成功率 + P95 + 吞吐(RPS)
- 压测数据量要接近真实（3 条向量压不出暴力扫描问题）

### 3.3 性能三查（上线前）

1. **连接池乘法账**：每副本 Hikari × maxReplicas ≤ PG max_connections；LLM 调用期间绝不占 DB 连接（禁止 @Transactional 里调 LLM）
2. **索引决策模板**：`做/不做 + 理由 + 触发条件`（本项目：3072 维无索引，数据到 5 万条前做低维重建；halfvec 路线的查询表达式匹配坑已记录）
3. **流式真实性**：任何 `collectList().block()` = 假流式；价值看 TTFT 不是总耗时

### 3.4 真实案例（Day74 压测报告）

- L1 底座：50 并发 100% 成功、**P95=14ms**（达标线 2s 的 1/143）
- L2 排查链（教科书）：单线程也失败（排除并发）→ embedding 直连 3/5 失败（锁定 micuapi 上游 60% 失败率）→ PG 正常（排除数据库）—— **分层排除法是标准动作**
- L3：100% 成功但 P50=7.4s —— 根因是 LLM 生成的物理时间，出路是缓存/流式/小模型，不是压代码

## 四、部署与发布维度（Day75/76 沉淀）

### 4.1 无状态化体检表（写代码时做，不是部署时）

| 内存态资产 | 外置方案 | 状态 |
|---|---|---|
| ChatMemory（InMemory） | JDBC 仓库 starter | 🔴 待改造 |
| BatchTaskStore（批量进度） | PG batch_task 表 | 🔴 待改造 |
| ReportFlowTools.DRAFTS（草稿） | 落库 + 审计 | 🔴 多副本直接坏（存 A 副本、发 B 副本"草稿不存在"） |
| NotificationTool.SENT（审计） | 落库 | 🟡 审计漏洞 |
| 两个答案缓存 | Redis（含语义缓存预留） | 🟢 多副本只降效不出错 |
| 灰度注册表（Day76） | DB + 管理界面 | 🟡 演示形态 |

### 4.2 探针语义（配错 = 连环重启雪崩）

- **liveness 只判进程活**（失败→重启容器）—— 放重逻辑 = 下游一抖全集群被 K8s 反复杀
- **readiness 判流量**（失败→摘流量不重启）—— 下游检查放这里
- initialDelaySeconds 给足（Spring 启动 20-40s，太短 = CrashLoopBackOff）

### 4.3 两个乘法账（部署前必算）

```
连接池：每副本 Hikari × maxReplicas ≤ PG max_connections（本项目 10×6=60 ✓）
限流：单机限流 × 副本数 = 实际总量 → 真限流要集中式（Redis/网关层，Day82）
```

### 4.4 发布与回滚 SLA

| 变更对象 | 发布方式 | 回滚 SLA |
|---|---|---|
| **提示词** | 版本注册表 + 按用户 hash 灰度 | **秒级**（percent=0，不重启） |
| 模型 | 双模型路由比例灰度 | 秒级 |
| 代码 | 镜像滚动更新（K8s） | 分钟级 |

### 4.5 真实案例

- **环境假设显式化**（Day75）：本机能构建 ≠ 镜像里能构建 —— toolchains 插件依赖本机 toolchains.xml，容器里必须生成（另：mvnw 在 JAVA_HOME=Java8 的终端里连 spring-boot:run 都加载不了，IDEA 却正常 —— 同一个"环境假设"主题）
- **gray×cache 冲突**（Day76 设计期预防）：回滚被缓存击穿 → 缓存 key 含版本维度
