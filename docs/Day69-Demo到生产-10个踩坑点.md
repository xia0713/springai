## 0. Demo 与生产的本质差距

先建立一个贯穿今天的框架 —— Demo 和生产的差距不是"代码质量"，是三个维度的质变：

| 维度 | Demo | 生产 |
|---|---|---|
| **质量** | 1 次调用成功 = 成功 | 1000 次/天，1% 失败 = 每天 10 个投诉 —— 质量从"一次性验证"变成"概率管控" |
| **治理** | 没有权限/审计/成本概念 | 权限、审计、成本上限是默认项，漏一项就是事故 |
| **运营** | 交付即结束 | 上线只是开始：谁维护、多旧失效、怎么迭代 |

**对应的失败原因也分三类：技术类（最好修）、治理类（要规范）、组织类（最难，多数项目死在这）。**

## 1. 核心知识点（40 分钟）：你的 10 个真实踩坑点

下面 10 个坑全部来自你 Day1-68 的真实经历（括号标注哪天踩的），每个都按"现象/根因/对策"整理 —— 这就是作业的示范样本。

### 技术类（5 个）

**坑 1：教程 API 和实际版本对不上**
- 现象：照着网上写 `Filter.builder()`，编译报错（Day44，你真实遇到）
- 根因：Spring AI 迭代快，网上的教程是旧版本 API
- 对策：**以本地 jar 为准**（javap 反编译验证签名再写）；集成类代码先写最小探针验证

**坑 2：框架默认行为和你的环境不兼容**
- 现象：官方推荐的 `MessageChatMemoryAdvisor` 组装出的消息把 System 挤到中间，网关 400 "System message must be at the beginning"（Day59，你真实遇到）
- 根因：框架的默认组装顺序假设了宽松网关；你的中转网关校验严格
- 对策：关键路径**控制权收归自己**（手动组装消息）；遇到"官方用法报错"先抓包看消息结构

**坑 3：工具异常炸穿请求**
- 现象：工具抛异常直接 500；手写循环里的 ToolCallingManager 不走容器降级 Bean（Day51/62）
- 根因：默认 alwaysThrow；手动构建的实例和 Spring 容器 Bean 是两套
- 对策：显式注册降级处理器 + 循环内 try/catch + 异常转人工介入单

**坑 4：模型猜值查出 0 行**
- 现象：NL2SQL 生成 `status='shipped'`，库里是"已发货"，永远查 0 行（Day52）
- 根因：枚举值没写进表结构说明，模型只能猜
- 对策：枚举值写全进注释/口径表；固定报表用参数化 SQL，不让模型写

**坑 5：Demo 代码污染生产数据**
- 现象：`RagTestCorpus.seed()` 里一句 `DELETE FROM vector_store` 全表清空 —— 这个测试类要是跑到生产库，真实文档全没（Day47 文档里警告过）
- 根因：Demo 代码和生产代码走同一条路径，没有环境隔离
- 对策：破坏性操作加环境守护（@Profile / 独立库 / corpus 标记删除）；上线检查单里必须有一项"演示代码已隔离"

### 治理类（3 个）

**坑 6：权限是"假的"**
- 现象：owner 过滤逻辑写好了，但"当前用户"来自前端参数；`/api/debug/**` 接口无鉴权裸奔（Day45/55 自查发现）
- 根因：Demo 阶段图省事，权限只在"看得见的入口"做了，鉴权来源和旁路入口没管
- 对策：全链路过滤盘点（入库/检索/问答/debug）+ 上线检查单逐项收口（Day82 换登录态）

**坑 7：演示残留忘收**
- 现象：KnowledgeSearchTool 的 owner=null 演示开关、MemoryTool 固定 zhangsan、内存态 ChatMemory、demo_orders 种子数据（Day63 的"三把刀"）
- 根因：演示开关是散落的，没有清单化管理
- 对策：所有演示开关集中登记成清单，上线前逐项收刀

**坑 8：失控无兜底**
- 现象：Agent 死循环烧 token、异常直接炸、成本无上限（Day57 可靠性数学 + Day62 防护前的状态）
- 根因：只写了 Happy Path，把异常当罕见事件
- 对策：步数/重复调用/耗时/异常四层熔断 + 人工介入单 —— 防护是默认项不是可选项

### 组织类（2 个）

**坑 9：没有基线就调优**
- 现象：改一版 prompt"感觉好了"，又说不出好在哪；上线后无法证明效果（Day47/60/68 反复强调）
- 根因：把调优建立在单次感受上，没有固定测试集和基线数字
- 对策：固定测试集 + 上线前测基线 + 单变量改动 + 每次改完跑回归

**坑 10：算不清账**
- 现象：项目做完了，老板问"省了多少"答不上；没有验收点，收尾变扯皮（Day68）
- 根因：立项时只想功能，没想"怎么算成功"
- 对策：验收点（指标+时间+测量方式）+ 敏感性检验 + 假设回填机制

## 2. Demo 到生产的核心差距（总结成三句话）

1. **质量从验证变管控**：Demo 证明"技术上可行"，生产要求"概率上可控" —— 靠测试集、熔断、降级、监控四件套
2. **治理从可选变默认**：权限、审计、成本上限、密钥管理不是加分项，是上线门槛 —— 靠上线检查单
3. **运营从结束变开始**：知识 Owner、SLA、迭代预算不是锦上添花，是项目活过 3 个月的条件 —— 靠验收点和回填机制

## 3. 企业 AI 化的正确推进路径

```
POC（1-2 周）──────→ 试点（1-2 月）──────→ 扩域（持续）──────→ 运营（永久）
技术验证，允许脏       窄场景 + 测试集         数据说话，逐域复制     Owner/SLA/迭代预算
不求生产质量           基线 + 验收点           每域先测基线           采纳率是生命线
```

**反模式对照（多数失败项目怎么死的）：**

| 反模式 | 后果 |
|---|---|
| 一步到位建全公司大平台 | 没有试点数据，老板信不过，冻结 |
| Demo 直接上生产 | 坑 1-8 全部引爆 |
| 只建不管 | 3 个月后知识库变垃圾场，没人信答案 |
| 没有 Owner 和 SLA | 运营是口头承诺，实际没人干 |

**你现在的位置**：你已经走完 POC 并完成了试点的技术侧（35 天原型 + 评测 + 防护），下一步动作就是**给试点定验收点 + 找知识 Owner** —— 这两件事比继续加功能重要。
