## 0. 为什么这两个场景值得单独一天

内容生成和审核是**企业里最高频的 AI 应用**（比 RAG 还高频）：

```
生成侧：客服回复话术、问题件客户通知、运营文案、周报、工单回复模板……
审核侧：用户生成内容合规、生成内容的质检、数据报表的口径校验……
```

而它俩是一对：**生成的越多，越需要审核**。今天把这对场景的架构一起讲透。

## 1. 核心知识点（40 分钟）

### 1.1 内容生成的三档形态（温度、约束、风险完全不同）

| 形态 | 例子 | temperature | 约束 | 幻觉容忍度 |
|---|---|---|---|---|
| **自由生成** | 营销文案、头脑风暴 | 0.7-0.9 | 弱（风格要求） | 较高（错了改就是） |
| **受约束生成** | 客服回复话术、问题件客户通知 | 0.2-0.3 | 强（基于知识库 + 业务规范） | **零**（答复口径错 = 事故） |
| **结构化生成** | 数据周报、表格、代码 | 0.1 | 极强（数据来自查询、格式固定） | 零（数字必须来自 DB） |

**关键判断：业务场景属于哪一档，决定 temperature、是否接 RAG、是否人工审核。** 大多数企业场景是后两档 —— "生成"其实是"受约束的改写"。

### 1.2 生成系统的五个技术要点

1. **数据要素走工具，不走模型记忆**：文案里的价格/日期/单号必须来自查询（Function Calling / 模板变量注入），模型只负责组织语言 —— 这是防幻觉参数的根治手段（Day54 的原则场景化）
2. **few-shot 喂"好例子"**：品牌规范和历史优秀文案入库，生成时检索 2-3 条做范例（Day23 的 few-shot + RAG 的合体）
3. **结构化输出 + 校验**：要求输出 JSON/固定字段，`BeanOutputConverter` 解析 + 校验必含要素（Day12）
4. **自检循环**：生成 → 规则校验 → LLM 自检（口径一致？要素齐全？）→ 不合格自动重生成（≤2 次，防死循环 —— Day62 的步数思想）
5. **人工闸门分层**：高危场景（对外公告）必审；低危（内部草稿）抽审 —— Day62"人工介入"的场景化

### 1.3 审核场景的分层架构（今天的判断力核心）

**一句话原则：审数据用代码，审语义用模型，审后果用人工。**

```
┌─ 规则层（代码实现，免费、确定、毫秒级，拦截 ~80%）
│    敏感词黑名单 / 长度格式 / 必含要素 / 正则（手机号、金额格式）
│    ↓ 存疑的才往下走
├─ 语义层（LLM，temperature=0，处理变体和意图类违规）
│    输出必须结构化：{判定: pass|fail|suspect, 违规类型, 置信度, 理由}
│    ↓ 高风险/低置信度的才往下走
└─ 人工层（高危必审 + 申诉复核）
     审核理由必须给人看（"涉及竞品负面表述"而不是"违规"）
```

**三条工程要点：**
1. **规则前置是成本关键**：审核是高频调用，规则层拦掉大头，LLM 只看 20% —— 直接决定账能不能算平
2. **误杀比漏杀更疼**：拦错正常内容，业务方马上炸 —— 所以判定必须带理由 + 可申诉；阈值宁松勿严
3. **数据校验别用 LLM**：报表数字对不对、字段类型对不对，代码做（确定性）；LLM 只解释异常、给修复建议（Day60"工具给事实"的同源原则）

### 1.4 两个场景的风险对照表

| 风险 | 生成侧 | 审核侧 |
|---|---|---|
| 头号风险 | **幻觉参数**（编造价格/日期） | **误杀**（拦掉正常内容） |
| 第二风险 | 口径不一致（各处生成各说各话） | 变体绕过（换个说法就漏） |
| 根治手段 | 数据走工具 + RAG 注入规范 | 规则+语义双层 + 申诉回流 |

## 2. 实操作业（80 分钟）："智能运营文案生成"系统架构图

> 目标：一页架构图 + 每模块的职责/选型/风险三要素。结合你的业务写（客服回复话术、问题件客户通知、内部周报都是真实场景）。

### 架构图模板（每层标注职责/选型/风险）

```markdown
# 智能运营文案生成系统架构

## 输入层
- 职责：运营选场景模板（客服话术/客户通知/周报）+ 填业务参数（单号/商品/活动）
- 选型：Web 表单 / 工单系统内嵌入口
- 风险：参数缺失 → 前端必填校验

## 素材层（RAG）
- 职责：检索品牌规范、业务口径、历史优秀文案 2-3 条（few-shot 素材）
- 选型：PgVector + 已建 RAG 链路；文案范例单独建 corpus 标记
- 风险：检索不准拉低生成质量 → 评测集监控命中率

## 生成层
- 职责：PromptTemplate 组装（变量+few-shot）→ LLM 按场景温度生成
- 选型：客服话术 0.2（受约束）/ 营销文案 0.8（自由）；qwen 系列
- 风险：幻觉参数（编价格日期）→ 数据要素由查询工具注入，模型不猜

## 质检层（自动）
- 职责：规则校验（长度/敏感词/必含要素）→ LLM 自检 → 不合格重生成 ≤2 次
- 选型：代码规则 + LLM 自检（结构化输出判定+理由）
- 风险：重生成死循环 → 次数上限（Day62 思想）

## 审核层（人工）
- 职责：高危场景必审（对外通知）、低危抽审；审核台展示修改建议
- 选型：工单系统已有审核流复用
- 风险：审核成为瓶颈 → 抽审比例按采纳率动态调

## 反馈层（运营闭环）
- 职责：采纳/修改率统计回流 → few-shot 池更新 + prompt 迭代
- 选型：埋点 + 周报；Day47 评测体系监控质量漂移
- 风险：只建不管 → 采纳率三个月后腰斩（和知识库同一个生死题）
```

### 三个硬要求

1. **每层必须写出"风险 + 对策"** —— 只画 Happy Path 的架构图不叫方案
2. **生成温度按三档形态标出来** —— 这是判断你懂不懂场景的试金石
3. **找一个你工作里真实的生成场景填进去**（如"问题件客户通知生成"），把单号/状态等要素标成"来自工单查询，不走模型"

## 3. 自检标准（不通过不许进 Day66）

- [ ] 架构图六层齐全，每层有职责/选型/风险三要素；
- [ ] 能讲清三档形态的温度与约束差异，并说出你的场景属于哪档；
- [ ] 能讲清审核分层原则："审数据用代码，审语义用模型，审后果用人工"，以及为什么规则层前置是成本关键；
- [ ] 能指出生成侧头号风险（幻觉参数）的根治手段（数据走工具）；
- [ ] 填了一个自己业务里的真实场景。

---

## 4. 提醒

1. **别把审核全交给 LLM** → 成本爆炸 + 误杀失控。规则层拦截 80% 是方案能否算平账的关键。
2. **别忽略反馈层** → 生成系统不是建完就完，采纳率是它的"知识库运营机制"（Day64 生死题的场景版）。
3. **结构化判定是审核落地的门槛** → "违规"两个字没法接系统；`{判定,类型,置信度,理由}` 才能进工单流。
