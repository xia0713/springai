# 企业 AI 工具调用设计规范（v1.0）

> 适用范围：所有通过 Function Calling（Spring AI `@Tool`）暴露给大模型的工具设计与实现
> 技术栈：Spring Boot 3.4.4 / Spring AI 1.0.3 / Java 21
> 维护人：zt23006 · 建立日期：2026-09 · 评审周期：每季度
> 核心原则（一句话）：**模型只表达业务意图，工具代码消化一切细节并守住边界。**

---

## 一、工具选型规范：什么逻辑做成工具

### 1.1 判定标准

只有**模型做不了或做不稳**的事，才做成工具：

| 做成工具 ✅ | 不做成工具 ❌（交给模型） |
|---|---|
| I/O：查库、调外部 API、读文件 | 写文案、写分析、写总结 |
| 确定性计算：四则运算、统计聚合 | 情感判断、"感觉类"评估 |
| 有副作用的系统操作：发通知、建工单 | 纯格式转换 |
| 需要鉴权/权限的数据访问 | 常识问答 |

**上线前必答的一问：这件事为什么不让模型直接做？答不出来就不该做成工具。**

### 1.2 设计细则

1. **单一职责**：一个工具一个业务动作。可独立重试、独立控权。
   - 反例：「查订单并通知用户」必须拆成两个工具。
2. **粒度适中**：按"一个业务动作"切分。过细 → 模型多轮切换浪费 token；过粗 → 鉴权无法收窄。
3. **描述即接口**：`@Tool(description)` + `@ToolParam(description)` 就是模型眼中的 API 文档，标准四要素：
   - 做什么（一句话）
   - 参数含义与取值范围（枚举值写全！）
   - 何时使用
   - **何时不用**（抑制误触发的最有效手段）
4. **固定 SQL 优先**：固定报表类查询，SQL 写死在工具内参数化传参；只有"任意查询需求"才让模型生成 SQL（且必须过校验器）。

## 二、安全规范：边界与红线

### 2.1 红线清单（一票否决，绝对禁止开放给 AI）

| # | 禁止操作 | 对应事故类型 |
|---|---|---|
| 1 | 无校验的数据库写操作（INSERT/UPDATE/DELETE/DROP） | 删库、数据篡改 |
| 2 | 资金操作（支付/退款/转账） | 资损 |
| 3 | 用户权限/角色变更 | 越权 |
| 4 | 生产配置修改、服务重启、发布上线 | 生产事故 |
| 5 | 文件/数据的删除类操作 | 数据丢失 |
| 6 | 任意收件人的邮件/短信/群发 | 骚扰、泄露 |
| 7 | 任意代码/Shell 执行 | 远程代码执行 |

### 2.2 强制要求

1. **只读默认**：新工具默认只读；写操作必须单独评审后上线。
2. **白名单**：写操作的目标对象（收件人、目标资源）必须白名单校验，白名单外**返回拒绝文本**（模型可转述），不静默失败。
3. **人工介入**：不可逆 + 高危操作走「AI 生成草稿 → 人确认 → 执行」。
4. **最小权限**：工具使用固定的低权限服务账号，绝不复用用户的全量权限；NL2SQL 类场景生产必须只读数据库账号（三层防线的最后兜底）。
5. **密钥不出上下文**：API Key/Token 只存在于配置和工具代码，绝不写入 prompt、绝不出现在工具参数中。
6. **操作顺序**：多步流程中，不可逆操作放最后（前面失败重试零成本）。
7. **审计留痕**：每次工具调用记录日志（谁 / 何时 / 什么工具 / 什么参数 / 结果 / 耗时），生产落库可追溯。

## 三、性能与稳定性规范

1. **超时必配**：所有外部 HTTP 调用必须显式设超时（建议 connect 3s / read 5s），禁止默认值裸奔。
2. **异常降级**：全局注册 `ToolExecutionExceptionProcessor(alwaysThrow=false)`，工具异常转为错误信息回传模型生成友好提示；禁止异常直接炸成 HTTP 500。
3. **错误分级**：可预期错误（格式错、不存在、越界）返回提示文本；意外故障才抛异常走降级。
4. **重试纪律**：重试只用于幂等操作；不可逆操作禁止自动重试，用补偿或人工确认。
5. **循环上限**：单请求最大工具调用轮数必须设上限（建议 10），防模型死循环烧钱（当前待实现，见 §7）。
6. **结果防线**：外部返回必须"挑字段 + 限条数（建议 ≤5）+ 转 Markdown 表格"；大结果走「显式存储 + 引用 ID」。

## 四、成本规范：Token 与调用优化

1. **按场景注册工具**：每个 Controller/ChatClient 只挂该场景需要的工具（每个工具的 description 都占每次请求的 token）。
2. **多步流程的清醒认识**：N 步工具流程 ≈ N 次完整 LLM 请求，上下文逐轮膨胀 —— 步数是成本的第一决定因素。
3. **description 精炼**：单工具描述 ≤100 字，写清边界即可，别写小说。
4. **低温**：工具选择、SQL 生成类请求 temperature ≤ 0.3。
5. **月度盘点**：统计各工具调用次数 × 平均 token，Top5 列入优化清单。

## 六、真实踩坑案例（均为本项目实测复现）

1. **description 雷同 → 模型选错工具**：三个工具都写"查询"，模型随机选。解法：描述互相区分得开 + 写清"何时不用我"。（Day51）
2. **除零异常炸请求**：工具抛异常直接 500。解法：`alwaysThrow(false)` 全局降级，错误信息回传模型友好提示。（Day51）
3. **模型猜枚举值查出 0 行**：NL2SQL 生成 `status='shipped'`，库里是中文"已发货"。解法：表结构注释里枚举值写全。（Day52）
4. **诱导写库**：用户问"把订单状态改成已签收"，模型真的可能生成 UPDATE。解法：白名单 SELECT + 黑名单关键字 + 禁分号三层代码校验。（Day52）
5. **800KB JSON 直接回传**：token 爆炸 + 模型迷路。解法：挑字段 / 限条数 / 转表格。（Day53）
6. **模型编造参数编码**：传 `deptCode=yanfa` 接口 404。解法：编码映射白名单，模型只给业务词。（Day53）
7. **大中间结果走上下文**：报告几千字在多步流程里滚多遍。解法：存 store 只传引用 ID。（Day54）

## 七、新工具上线检查单（评审用）

```markdown
## 新工具上线评审单
工具名称：____________        申请人：______

【选型】
□ 说明了"为什么不让模型直接做"
□ 单一职责，粒度为一个业务动作
□ description 含四要素（做什么/参数/何时用/何时不用）

【安全】
□ 不在红线清单内；写操作已单独评审
□ 写操作目标对象有白名单校验
□ 鉴权密钥只在配置/代码，未进 prompt
□ 使用低权限账号；有审计日志
□ 不可逆操作有草稿/确认机制，且位于流程末尾

【性能】
□ 外部调用已配超时
□ 异常走降级通道，错误信息可读
□ 重试策略与幂等性匹配

【成本】
□ 只在需要的场景注册
□ 返回结果已格式化/截断，大结果走引用传递
□ 请求 temperature ≤ 0.3（工具类）

结论：□ 通过  □ 整改后通过（整改项：______）  □ 拒绝
```
