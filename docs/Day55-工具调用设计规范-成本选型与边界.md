## 2. 核心知识点（40 分钟）

### 2.1 成本与性能优化 —— 每次工具调用都是真金白银

先理解**钱花在哪**：

```
一次带工具的调用 = system prompt + 工具清单(所有工具的 description + 参数 schema)
                 + 对话历史 + 工具返回结果
   ↓ 而且
多步流程（Day54 的 4 步）= 每一步都是一次完整的 LLM 请求！
   4 步流程 ≈ 4 次 LLM 调用，上下文越滚越大
```

**六个优化手段（按性价比排序）：**

| # | 手段 | 说明 | 你哪天已经做过 |
|---|---|---|---|
| 1 | **只注册该场景需要的工具** | 每个工具的 description 都占每次请求的 token。查报表的 Controller 别挂天气工具 | —（今天记住） |
| 2 | **结果格式化/截断** | 800KB JSON → 5 行表格 | Day53 |
| 3 | **大结果引用传递** | 存 store 只回传 ID | Day54 |
| 4 | **description 精炼但具体** | 一两句话说清"干什么+何时用+何时不用"，别写小说 | Day51 |
| 5 | **低温** | 工具选择和 SQL 生成要确定性，temperature 0.1 | Day52 |
| 6 | **限制工具循环轮数** | 生产要设置单请求最大工具调用次数（如 10 次），防模型死循环烧钱 | Day62 会做熔断 |

> 进阶（知道即可，Day72 成本优化再细化）：模型分层 —— 简单的"选哪个工具"路由用小模型，复杂推理才用大模型。

### 2.2 工具选型 —— 什么逻辑适合做成工具？

**判断标准一句话：模型做不了或做不稳的事，才做成工具。**

| 适合做成工具 ✅ | 不适合 ❌（交给模型/提示词） |
|---|---|
| I/O：查库、调 API、读文件 | 写文案、写分析、总结 |
| 确定性计算：四则运算、统计聚合 | "感觉类"判断（情感分析用模型更准） |
| 有副作用的系统操作：发通知、建工单 | 纯格式转换（让模型直接输出） |
| 需要鉴权/权限的数据访问 | 模型本来就会的常识问答 |

**三条选型细则：**
1. **单一职责**：一个工具干一件事。"查订单并通知用户"是两个工具（拆开才能各自重试、各自控权）
2. **粒度适中**：太细（getOrderId/getOrderStatus/getOrderAmount 三个接口）→ 模型来回切换浪费轮次；太粗（manageOrder 干十件事）→ 鉴权没法控。按"一个业务动作"切
3. **描述即接口**：工具的 `description` + `@ToolParam` 就是模型眼中的 API 文档。接口没写清楚 = 模型的"使用说明书"缺页

### 2.3 边界控制 —— 哪些操作绝对不能开放给 AI（红线清单）

**最高优先级的一节。** 以下是红线（生产环境直接抄进规范）：

```
🚫 绝对不能开放给 AI 的操作：
1. 无校验的数据库写操作（INSERT/UPDATE/DELETE/DROP）
2. 支付、退款、转账类资金操作
3. 用户权限/角色变更
4. 生产配置修改、服务重启、发布上线
5. 文件系统/存储的删除操作
6. 任意收件人的邮件/短信/群发（必须白名单 + 人工确认）
7. 任意代码/Shell 执行
```

**四条边界原则：**

| 原则 | 含义 | 实证 |
|---|---|---|
| **只读默认** | 新工具默认只读，写操作单独评审才上线 | Day52 NL2SQL 校验器 |
| **白名单** | 写操作的参数（收件人、目标对象）必须是白名单 | Day51/54 通知与邮件 |
| **人工介入** | 不可逆 + 高危 = AI 生成草稿 → 人确认 → 执行 | Day54 草稿模式，Day62 展开 |
| **最小权限** | 工具用固定的低权限服务账号，不是用户的全量权限 | Day52 只读账号，Day82 深化 |

四维度结构，每个维度 = 原则 + 红线 + 自查清单。直接开写。

## 3. 实操作业（80 分钟）

> 目标：产出《企业 AI 工具调用设计规范》，四大维度齐全，团队可直接用。

### 步骤 1：新建 `docs/企业AI工具调用设计规范.md`，按下面模板写

```markdown
# 企业 AI 工具调用设计规范（v1.0）

> 适用范围：所有通过 Function Calling 暴露给大模型的工具设计
> 维护人：xxx · 评审周期：每季度

## 一、选型维度：什么做成工具

1. 只有"模型做不了或做不稳"的事才做成工具（I/O、确定性计算、系统操作）
2. 单一职责：一个工具一个业务动作；可独立重试、独立控权
3. 粒度适中：按业务动作切分，避免过细（多轮次）或过粗（无法控权）
4. description 标准：做什么 + 参数含义 + 何时使用 + **何时不用**（各一句话）
5. 自查：新工具上线前回答——"这件事为什么不让模型直接做？"

## 二、安全维度：边界与红线

🚫 绝对禁止开放（红线清单，一票否决）：
- [ ] 无校验的数据库写操作
- [ ] 资金操作（支付/退款/转账）
- [ ] 权限变更、生产配置、发布上线
- [ ] 删除类操作（文件/数据）
- [ ] 任意收件人的消息发送
- [ ] 任意代码/Shell 执行

强制要求：
- [ ] 只读默认：写操作需单独评审
- [ ] 白名单：写操作的目标对象必须白名单校验
- [ ] 人工介入：不可逆操作走"草稿→确认→执行"
- [ ] 最小权限：工具使用低权限服务账号
- [ ] 密钥不出上下文：鉴权在工具代码内完成
- [ ] 审计日志：每次工具调用记录（谁/何时/什么工具/什么参数/结果）

## 三、性能维度：稳定性设计

- [ ] 外部调用必须配超时（建议 connect 3s / read 5s）
- [ ] 异常降级：注册 ToolExecutionExceptionProcessor(alwaysThrow=false)，
      错误信息回传模型生成友好提示，禁止 500 裸奔
- [ ] 可预期错误返回提示文本；意外故障才抛异常
- [ ] 重试只用于幂等操作；不可逆操作用补偿/人工确认
- [ ] 单请求最大工具调用轮数上限（建议 10，防死循环）

## 四、成本维度：Token 与调用优化

- [ ] 按场景注册工具：每个 Controller/ChatClient 只挂该场景需要的工具
- [ ] 结果必须格式化：挑字段、限条数（建议 ≤5）、转 Markdown 表格
- [ ] 大结果引用传递：存 store/DB，只回传 ID
- [ ] description 精炼：单工具描述建议 ≤100 字
- [ ] 工具调用类请求 temperature ≤ 0.3
- [ ] 每月统计：各工具调用次数 × 平均 token，找出 Top5 优化对象

## 五、附：真实踩坑案例（从我们项目里来的）

1. description 雷同导致模型选错工具 → 多工具必须边界清晰（Day51）
2. 除零异常炸请求 → alwaysThrow(false) 降级（Day51）
3. 模型猜枚举值 'shipped' 查出 0 行 → 枚举值在表结构里写全（Day52）
4. 800KB JSON 直接回传烧 token → 挑字段/限条数/转表格（Day53）
5. 邮件重复发送风险 → 不可逆操作放流程最后 + 白名单（Day54）
```

### 步骤 2：对照自己项目自查一遍

拿这四维度逐条对照你 Day50-54 写的 10+ 个工具，**每个工具过一遍红线清单**。发现不符合的当场修（比如：哪个工具日志没打全？哪个写操作没白名单？）。

### 步骤 3：给规范补充"你公司的真实约束"

模板是通用骨架，加 2-3 条你们公司的真实场景（如"对接 WOS 工单系统只允许查询类接口""禁止 AI 直接操作 Apollo 配置"）—— 有真实约束的规范才是能落地的规范。
